# Weekly 150: project progress and handoff

Last updated: 2026-10-24. Read this first in a new session, then the files it points to.

## What this is

Weekly 150 is a single-page web app that gets people to exercise regularly. It works as a pocket training log built around the WHO 2020 physical activity guideline. It is one self-contained HTML file, `weekly-150.html`, published as a private claude.ai Artifact:

- Live page: https://claude.ai/artifact/BLA3m85d4r3qry7wFm4UTa (version 5 is current)
- Visual identity: a track meet. Paper race bib, blue track band with lane lines, results-sheet tables. Fonts: Barlow Condensed (display), Barlow (body), IBM Plex Mono (labels and numbers).
- In the Artifact, all user data lives in the visitor's browser (localStorage). There is no backend. The web version (see "Web version") adds accounts and a Supabase backend.

### Accounts and auth flows

- **Register:** username (`^[a-z0-9_]{3,20}$`, lowercased and trimmed, never changeable, primary key of `profiles`), display name (1 to 40 after trim), age (whole 0 to 120), email, password (8 or more, must match "verify password"). `signUp` carries username, display name and age as user metadata; the DB trigger `handle_new_user` validates them, creates the profile and a `w150.prefs` row with the age. A taken username gives `Username taken.` (checked on blur through `username_available`; when sign-up answers 500 the app asks `username_available` again and shows `Username taken.` only if it is now taken, otherwise `Something went wrong. Try again.`, so an email-send failure is not blamed on the username).
- **Verify email:** confirmation is required before the first login. The link returns to the app, which shows `Email verified. You can log in now.` An unverified login gets `Email not verified yet.` with a resend button.
- **Login:** the browser posts username and password to `auth-login`. The function resolves the username through `public.profiles` (never user metadata), checks the password with GoTrue and returns only a session (no email). Unknown user and wrong password both answer `Wrong username or password.`, and every failure is padded to 400 ms. The app then calls `setSession`.
- **Forgot password and resend:** `auth-recover` always answers `If that account exists, we sent an email.` (body and timing do not depend on whether the account exists). The reset link opens the reset screen; the new password is saved with `updateUser` and other sessions are signed out. An expired or used link shows `This link has expired or was already used. Request a new one.` on the forgot screen, never a blank page.
- **Rate limits:** 10 failed logins per username and 30 per IP in 15 minutes (reserve then release, so a parallel burst cannot exceed it); recovery 3 per identifier and 10 per IP. Answer: `Too many attempts. Try again in a few minutes.` Counted in `public.auth_attempts`.
- **Logout:** flushes pending writes (at most 3 s), `signOut({ scope: 'local' })` (this device only), resets the store. A tab that holds one user's queue resets and reloads when another user signs in.
- **Session expiry while the app is open:** supabase-js refreshes the token; a write that fails with 401 is retried after `refreshSession()`; only a failed refresh shows the login screen (`Your session ended. Log in again to keep saving.`). Pending writes stay in memory and are flushed after the same user logs in again.
- **Sync status** (`#sync-status`): Saving, Saved, `Not saved, retrying` (backoff 1, 2, 4, 8, 16, 30 s). `beforeunload` warns while writes are pending. Two tabs or devices merge sessions by id; a session deleted in one place stays deleted.

### Storage

| Key or table | Where | Notes |
|---|---|---|
| `w150.meta`, `w150.sessions`, `w150.plan`, `w150.prefs`, `w150.breaks`, `w150.tracks` | `public.user_data`, one row per user and key, `version` (bigint) for compare and set (RLS: own rows only) | Same shapes as the Artifact table further down. Writes go through `put_user_data(key, value, expected_version)`; every insert and update takes a new version from the global sequence `public.user_data_version_seq`, so a version is never reused, even after Clear all deletes a row and it is inserted again (versions are compared for equality only and have gaps). A null value (no plan) is stored as JSON null. `w150.tracks` saves `{}` instead of deleting when empty. Clear all keeps the age. |
| `w150.theme` | browser localStorage | Not synced. |
| `public.profiles` | server | username (primary key), display name. The owner can read it and change the display name only; no client insert or delete. |
| `public.auth_attempts` | server | Service role only. Rate limit counters; never pruned yet (see open items). |

### Edge Functions

- `auth-login` (POST `{ username, password }`): 200 `{ session }`, 400 bad request, 401 wrong credentials, 403 email not confirmed, 429, 500 `server_error` for GoTrue or database problems (not counted as a failed login).
- `auth-recover` (POST `{ identifier, action: 'reset' | 'resend', redirectTo }`): always 200 neutral copy for a valid request; 400 for bad input or a `redirectTo` outside `AUTH_REDIRECT_ORIGINS`; 429.
- Both are deployed with `--no-verify-jwt`. They use the service role key that the Supabase runtime provides; it never appears in the repo or in `web/`.

### Decisions worth knowing (rulings during the build)

- The Artifact is frozen; the web app is a fork with an injected store, so exercise rules and `credit()` stay identical.
- Merge uses a three-way delete rule: an item that is in the base copy but missing on the server was deleted elsewhere and is dropped, unless the local copy was edited (then the local edit wins).
- On a version conflict for keys other than sessions and tracks, the server wins; the notice `Another device saved a newer version, so your last change was replaced.` shows only when this device had really changed that value (the app rewrites unchanged keys on every save).
- Versions come from one global sequence, never restart at 1 after a delete (no ABA between Clear all and a stale device).
- Seeded sample sessions have fixed ids `sample_0` to `sample_33` and times taken from today's date (sample plan too), so two devices seeding a brand-new account at once merge to one sample.
- Anon cannot read any table (error 42501 instead of 0 rows), stricter than the original brief.
- Login rate limit is reserve then release, not check then insert. Only `invalid_credentials` counts as a failed login; other GoTrue errors answer 500.
- Logout signs out this device only. The display name shows on the race bib at every width and in the header from 1100px.
- Local `config.toml` raises `email_sent` to 60 and `sign_in_sign_ups` to 300 for testing only. The cloud needs custom SMTP, the default `email_sent`, and a raised `sign_in_sign_ups`, because every login comes from the function's one egress IP (see `docs/deploy.md`).
- The Supabase stack uses the default 543xx ports; another local Supabase project on those ports must be stopped first.
- `weekly150-web` runs `node tools/web/serve.js` because python is not on PATH on this machine. `weekly150-preview` (Artifact) still uses python.
- Functions are served locally with `npm run functions:serve`; the stack that was running during the build started before the function folders existed and did not serve them.

## Features (current state)

1. **Age first, age-based targets (A).** The visitor enters an age before targets apply. One `GUIDE` table drives everything:
   - 5 to 17: 420 min/week (60 a day), vigorous counts 1:1, muscle and bone strengthening 3 days, vigorous 3 days.
   - 18 to 64: 150 min/week credit (moderate + 2 x vigorous), muscle strengthening 2 days, stretch goal 300.
   - 65+: as adults, plus balance days 3 per week.
   - Under 5: no targets, link to the WHO under-5 guideline.
2. **Strength counted separately (B).** Strength sessions count as muscle days only, never as aerobic minutes.
3. **Light activity (C).** Light effort can be logged and is shown, but never counts toward the target.
4. **Balance for 65+ (D, G).** "Balance days: N of 3", activities Balance or tai chi and Dance, a "this session included balance work" checkbox, the "Steady feet" routine. A session counts only at moderate effort or more.
5. **Sit less (E).** WHO sedentary advice per age group, "I got up and moved" counter (per day, own storage key), optional nudge every 30 minutes while the page is open. Artifact only: removed from the web version (log entry K); `w150.breaks` is no longer read or written there, Clear all still deletes it.
6. **Stretch goal (F).** After 150, adults and 65+ see progress toward 300.
7. **GPX import (H).**
   - Import GPX button and drop zones, several files at once.
   - Review card before saving: activity, date, minutes and effort are editable. Effort comes from HR % of max when the file has HR and the age is known, otherwise from speed.
   - Saved as a normal session (`source: 'gpx'`, `trackId`), so all rules apply.
   - Detail view: stats, SVG route coloured by HR or speed (no map tiles, OpenStreetMap link instead), pace/speed, elevation and HR charts with a shared crosshair, per km / 5 km / 100 m splits, and the device-total note.
   - Imports from other weeks appear under "Earlier imports".
8. **Always there:** sample data on first visit (clearly marked, cleared by the first real entry), Undo on remove, inline confirms, theme toggle Auto/Light/Dark, 400px layout.

## GPX notes

- The real Mi Fitness file has lat, lon and time only (no ele, HR, cadence). Its header says `totalDistance` 5052 m but the points add up to 2.02 km in 13:27 (6:39 /km). The file name ends in `_01`, so it is probably one part of a split export. The page computes from the points and shows a note.
- Its start time is 18:48 UTC, which is Wed 7 Oct 01:48 in UTC+7, so it lands on 7 Oct (date is editable in the review card).
- Thresholds (`GPX_THRESHOLDS` in the page): HR moderate 64 to 76% of max, vigorous 77%+, max HR 220 minus age (Tanaka 208 minus 0.7 x age under 18). Speed: walk 4.0 / 7.2 km/h, run 4.2 / 6.4, cycle 16.1 vigorous, swim crawl 1.6 / 2.6, open water vigorous. The CDC HR percentages are Secondary (taken from a search excerpt).
- Pool swims without GPS points are rejected with a plain message.
